
# 下游生命周期以领域聚合根中的单一权威状态为准

下游是否就绪目前存在两个独立真相源：领域聚合根从 `_downstream_ready` 与
`_downstream_shutdown` 两个 bool 派生的 `DownstreamState` 只用于呈现，而基础设施客户端
另持一个 `_downstream_ready` bool。重启、停机、唤醒、崩溃时领域先于基础设施翻转自己的
标志，代理门控读基础设施标志、派发门控与休眠判定读领域标志，同一时刻可能对同一概念
给出不同答案；日志也分裂为两套格式。

我们决定把下游生命周期提升为领域聚合根持有的单一权威值 `DownstreamLifecycle`，唯一改写
入口是 `transition(state, reason)`，合法转换表封装在 seam 内部。领域决策（重启、停机、
唤醒、崩溃）与基础设施观测（经 `DownstreamReadyChangedEvent`）都经此 seam，日志与权威
状态事件由 seam 统一产生，所有门控与呈现都读取同一权威状态。理由是该决策难以逆转
（跨层 seam 落地后所有读写都依赖它）、无上下文令人惊讶（为何两个事件、为何生命周期
住在聚合根而非 shared），且经真实权衡后排除过其他方案。

## Considered Options

- **把生命周期模块放进 shared 层，领域与基础设施都直接调用**：被否决。按项目约定
  shared 只放纯数据模型、异常与接口，且状态机流转必须定义在领域聚合根中；此方案会把
  状态机挪出聚合根并扩大 shared 职责。
- **保留基础设施为物理权威，领域只做事件镜像，去掉领域侧提前翻转**：被否决。重启期间
  必须同步翻转就绪标志以阻止系统休眠（否则系统闲置休眠会打断重启），ADR-0003 也要求
  停机判定定义在领域聚合根。
- **引入第四态 `FAILED/UNHEALTHY` 表达崩溃与卡死**：被否决。崩溃与卡死目前都归入
  STARTING，扩展该状态的领域含义即可消除语义冲突；新增状态会扩大门控改动面与对外
  契约，超出消除双真相源的范围。
- **单一事件由 seam 发布、基础设施反向调用领域上报**：被否决。会给基础设施开一条
  反向依赖通道；保留「基础设施观测事件 → 领域 seam → 权威状态事件」的事件链即可，
  依赖方向保持单向。
- **两套日志都保留、只统一格式字符串**：被否决。仍有两个输出点，达不到 locality 目标。

## Consequences

- `DownstreamClient` 抽象不再暴露 `downstream_ready`；代理门控改读领域权威状态，就绪
  等待逻辑订阅权威状态事件并以 `state == READY` 为成功条件。
- 保留 `DownstreamReadyChangedEvent` 作为基础设施到领域的物理观测事件；新增
  `DownstreamStateChanged(state, reason)` 由 seam 在成功转换后发布，供呈现层消费。
- `reason` 统一为 shared 层的枚举，仅用于日志与诊断，不进入 `GatewayState` 或 SSE
  对外状态契约；SSE 的状态值仍为 `ready / starting / shutdown`。
- 生命周期日志只有一个输出点（seam）；被拒绝的转换也记录并标注 `rejected=`，不视为
  异常；基础设施侧不再输出第二套就绪日志。
- `Starting（未就绪待恢复）` 的领域含义扩展为「下游未处于可服务状态且未停机」，涵盖
  启动或重启中、崩溃后待恢复、卡死待处置；`Shutdown（下游停机）` 仍与未就绪互斥。
