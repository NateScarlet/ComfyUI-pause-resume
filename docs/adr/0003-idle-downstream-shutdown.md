# 空闲时允许下游停机，按需冷启动

下游 ComfyUI 进程即使没有任务也会占用约 2GB 的启动基线内存；既有的空闲重启
（`COMFYUI_IDLE_RESTART_SEC`）只释放显存，终止后立即拉起新进程，内存随即被重新占用。
我们决定引入 **Shutdown（下游停机）**：下游进程被主动终止且不会自行恢复，只能由
活动结束。它与 Idle（网关业务状态）、未就绪（启动或重启中的临时态）是三个独立概念，
停机不是未就绪的一种，否则系统休眠阻止、空闲判定与派发判定都会把停机误读成
「正在启动」。

停机不是必选动作，而是用户授权的许可：勾选「空闲时允许下游停机」（默认关闭）后，
只有空闲窗口到期（由活动推迟）、队列完全为空、且系统可用物理内存连续 3 次采样低于
阈值（默认 1 GiB）时才停机；内存充足时回退既有空闲重启，下次空闲窗口到期再判。
唤醒也不再是一条命令，而是活动的副作用：任何代理请求在 Shutdown 状态下先于就绪检查
触发唤醒，再走既有等待与加载页逻辑。

## Considered Options

- **复用 `downstream_ready = False` 表达停机**：被否决。系统休眠阻止、空闲判定、
  派发判定都读取就绪标志，把停机塞进「未就绪」会让这三处同时把停机误判为
  「正在启动」，结果是永久阻止系统休眠、空闲永不成立、派发一直等待。
- **把空闲动作做成「重启 / 停机」二选一**：被否决。停机代价是用户下次要付完整
  冷启动时间，没有内存压力时不该强加；勾选是授权，内存是必要条件而非附属条件。
- **独立的手动停机入口与 `/start` 端点**：被否决。唤醒是活动的副作用，任何代理
  请求都应触发；停机时 ComfyUI 页面不存在，UI 里没有放「启动」按钮的位置。用户在用
  但需要立即释放资源时，直接通过托盘退出网关。
- **持久化当前是否停机**：被否决。会造成「重启了网关、下游却一直不回来」的
  难以察觉状态；不预热的需求已由 `COMFYUI_ON_DEMAND_START` 覆盖。
- **内存压力单独触发停机、不等空闲窗口**：被否决。用户正在使用（活动）时不应
  自动停机；空闲窗口已是「用户没在用」的既有判定，无需第二套口径。

## Consequences

- 停机判定必须定义在领域聚合根中；基础设施只负责终止与拉起进程的副作用，
  不得自行决定何时停机。
- 停机期间允许系统休眠，外部程序维持停机前的调度状态；`QueueState` 不新增值，
  它表达的是网关队列的运行状态而非下游进程状态。
- 勾选偏好持久化到状态数据库（沿用 `paused` 的持久化方式），并提供环境变量
  `COMFYUI_ALLOW_IDLE_SHUTDOWN` 作为无托盘部署的初始值；当前是否停机不持久化。
- `resume` 只管队列语义，不兼职唤醒；控制端点不计活动，请求入口在停机状态下
  先触发唤醒再进入就绪检查。
- 托盘「正在停止」（暂停后等当前任务完成）改名为「等待当前任务完成」，避免与
  「下游停机」混淆；托盘勾选文本固定为「空闲时允许下游停机」。
- 内存采样限定 Windows（`GlobalMemoryStatusEx`），不引入第三方依赖；
  `COMFYUI_IDLE_RESTART_SEC` 默认值与既有空闲重启行为保持不变。
