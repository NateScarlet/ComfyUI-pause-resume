
# 下游任务结束的权威信号与卡死检测

下游是否仍在执行任务，网关此前只依据下游日志中的 `got prompt` / `Prompt executed in`
两行文本判定。ComfyUI 消费任务队列的工作线程是唯一的；当它在执行中因异常逃逸而死亡
（例如 OOM 在错误清理路径上再次抛出，杀死工作线程），`Prompt executed in` 永远不会
打印，而下游进程本身仍然存活。结果是网关永远认为任务在执行，下游也永远不再消费任何
队列，系统失去自愈能力；既有的崩溃监控依赖进程退出，同样检测不到。

我们决定：继续以日志文本作为执行状态的唯一信号源，但补上「异常标记 + 收尾超时」的
卡死检测——观察到下游抛出执行异常后，若收尾超时内仍未出现正常收尾日志，即判定卡死。
卡死在下游处理能力丧失这点上与崩溃同构，因此复用崩溃语义：终止并重启下游进程、正在
执行的任务重新入列、并计入崩溃降级阈值。

## Considered Options

- **改用下游 API（`/queue`、`/history`）作为状态信号**：被否决。端点与返回结构同样随
  ComfyUI 版本漂移；且任务级 API 信号无法区分「长任务」与「卡死」——两种情况在队列与
  历史中都表现为任务长期不结束。
- **WebSocket 心跳**：ComfyUI 会向派发时指定的 `client_id` 推送 `progress_state`，工作
  线程死亡时推送立即停止，是真正的活体心跳。被否决的原因是它引入额外连接与 `client_id`
  生命周期管理，而本次要覆盖的场景已由异常标记精确命中；无异常原因的工作线程死亡在实践
  中不存在（内存耗尽会杀死整个进程，由既有进程存活检测捕获）。
- **仅重新入列、不重启下游**：被否决。工作线程死亡后下游不再消费任何队列，重新入列的
  任务只会永久滞留在下游队列中。
- **纯执行时长超时**：被否决。耗时越长的任务被误杀的代价越大，宁可漏判也不误判。

## Consequences

- 卡死归入「中断」而非「完成」，因此不写入预估时长（该次执行没有产出），与强制重启一致。
- 检测窗口只在已观察到异常标记的任务上开启，长任务不会进入该窗口，误杀概率为零。
- 收尾超时是「异常后收尾」的超时而非「执行时长」超时，取值保守（默认 1800 秒，可由
  `COMFYUI_STALL_TIMEOUT_SEC` 覆盖）。
- 无异常标记的工作线程死亡不被本机制覆盖；若未来出现此类场景，需回到本决策重新评估
  WebSocket 心跳方案。
